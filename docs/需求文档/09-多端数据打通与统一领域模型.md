# 多端数据打通与统一领域模型（客户 / 快递员 / 司机 三端共享数据源）

> 本文档是三端（客户小程序、快递员端、司机端）任务卡的**前置架构契约**。
> Claude Code 在实现任意一端的任意页面前，必须先读本文档。
> 违反本文档"硬性契约（§6）"的改动一律视为 bug，无论单端功能是否跑通。
> 🔧 2026-10-18 P2 收缩：§7 已完成的 P0-1 PRD 压缩为完成留痕（36.7KB→~14KB）；§1.1 实体物理表名订正为现行 `oms_/work_/iot_` 前缀；§4.3 映射表改指针（真源《07》§一）。

## 0. 为什么必须有这份文档（用户硬要求）

用户原话："几个用户端数据必须是通的"。含义：**客户下单 → 快递员取派 → 司机运输，整条链路共享同一份业务数据**，三端看到的是同一批记录的**不同投影（projection）**，不是三份独立数据。

成熟产品（顺丰"青龙"、京东物流、菜鸟、满帮、G7、货拉拉；溯源见 §9）共同指向三原则：

1. **单一数据源**：订单/运单/运输任务只有一份主记录，各端只读投影。
2. **统一 ID**：订单号即运单号即查询主键，靠稳定 ID 串联。
3. **统一状态机**：由状态机集中驱动（状态 + 子状态 + 原因码），严禁散落 `if/else` 与直接 `setStatus`。

本项目链路主键已存在；原"状态桥与轨迹查询断点"已修复（§3.2 / §4.1 实测）。本文档是三端共享数据的可执行契约。

## 1. 现状核对：真实实体与关联链路（基于代码，非设计）

以下实体与字段均来自 `xfwl-oms` / `xfwl-work` / `xfwl-netty` 实测代码，是"单一数据源"的物理落地。

### 1.1 实体清单

| 实体（表） | 模块 | 角色 | 关键字段 |
|---|---|---|---|
| `Order` (`oms_order`) | xfwl-oms | **客户订单主记录**，客户/快递员可见状态的载体 | `id`(订单号/运单号)、`memberId`、`paymentMethod`、`paymentStatus`、`amount`、`status`(1–12)、收/发件人信息 |
| `OrderCargo` (`oms_order_cargo`) | xfwl-oms | 货物明细 | `orderId`、`tranOrderId`(运单id)、`goodsTypeId`、`weight`、`volume` |
| `TransportOrder` (`work_transport_order`) | xfwl-work | 调度生成的运单 | `id`、`orderId`(外键→Order) |
| `TransportOrderTask` (`work_transport_order_task`) | xfwl-work | 运单↔运输任务关联 | `transportOrderId`、`transportTaskId` |
| `TaskTransport` (`work_task_transport`) | xfwl-work | **司机运输任务主记录**，司机可见状态的载体 | `id`、`truckId`、`status`(1–5)、计划/实际发车·到达·提货·交付时间、经纬度 |
| `DriverJob` (`work_driver_job`) | xfwl-work | 司机作业记录 | `id`、`driverId`、`taskTransportId`(外键→TaskTransport)、`status`(1–5) |
| `LocationRecord` (`iot_truck_location`) | xfwl-netty | GPS 轨迹明细 | `businessId`(车辆/快递员id)、`transportTaskId`、`type`(truck/courier)、`lng`、`lat`、`currentTime` |

> 单号说明：`Order.id` 由 `CodeGenerate` 生成 8 位编码，**同时充当客户查询用的"运单号"**。没有独立 `trackingNo` 字段——客户凭 `Order.id` 查全程。

### 1.2 关联链路图（单一数据源的物理串联）

```
客户 Order.id (运单号)
   │  orderId
   ▼
TransportOrder (运单)
   │  transportOrderId
   ▼
TransportOrderTask ── transportTaskId ──▶ TaskTransport.id (司机运输任务)
   │                                         │ taskTransportId
   ▼                                         ▼
OrderCargo (货物)                        DriverJob (司机作业)
                                           │
                                           ▼
                                      LocationRecord.transportTaskId (轨迹)
                                      LocationRecord.businessId (车辆/快递员 id)

客户可见状态  = Order.status        (12 级: 1~12)
司机可见状态  = TaskTransport.status (5 级: 1~5)  ↔ DriverJob.status
快递员操作对象 = Order (取件/派送阶段) + OrderCargo + POD
```

**结论**：三端在物理上已经指向同一批记录，链路主键完整。问题不在"有没有"，而在"状态怎么互相同步"和"客户怎么查到自己的轨迹"——见 §4、§5。

## 2. 三端投影模型（同一份数据，不同可见性）

| 端 | 读取的主记录 | 写操作 | 可见状态范围 |
|---|---|---|---|
| **客户端**（客户小程序） | `Order`（仅本人 `memberId`）、`OrderCargo`、`LocationRecord`（经 §5 解析） | 下单、支付、评价、查件 | `Order.status` 全 12 级（映射为**客户 7 档视图**，见 §4.3） |
| **快递员端** | `Order`（取件 1–4、派送 8–10）、`OrderCargo`、本人 `LocationRecord` | 取件确认、POD 电子签收、异常上报、派送 | 取件/派送阶段状态 + POD |
| **司机端** | `TaskTransport`/`DriverJob`（`driverId`=本人）、`LocationRecord`（本人 `businessId`） | 发车/到达/交付、轨迹上报、异常 | `TaskTransport.status` 1–5 + 轨迹 |

**铁律**：任何一端**不得**维护本端私有的"订单状态副本"。所有状态以 `Order.status` / `TaskTransport.status` 为准，前端只做展示映射。

## 3. 状态机打通契约（核心）

### 3.1 两套状态机必须可互相推导

| 业务阶段 | 客户/快递员可见 `Order.status` | 司机可见 `TaskTransport.status` / `DriverJob.status` | 状态变更触发方 |
|---|---|---|---|
| 下单·待取件 | 1 待取件 | （尚无运输任务） | 客户下单 |
| 已揽收 | 2 已取件 | — | 快递员取件 |
| 网点自寄/入库 | 3 / 4 | — | 网点 |
| 干线待发/运输中 | 5 待装车 → **6 运输中** | **2 进行中（在途）** | **司机发车 depart** |
| 到达终端网点 | **7 网点出库** | **4 已完成（交付）** | 司机交付 deliver |
| 到达待确认 | 7（不变） | **3 待确认（司机到达 arrive）** | 司机到达 arrive |
| 末端待派/派送中 | 8 待派送 → 9 派送中 | —（转入快递员域） | 快递员派送 |
| 已签收 | **10 已签收** | — | 快递员妥投 `delivered` |
| 拒收 | 11 拒收 | — | 快递员 |
| 取消 | 12 已取消 | 5 已取消 | 任一端（需权限） |

已被以下位置**实际调用**：
- `TaskTransportServiceImpl` 第 243 / 287 / 331 行（depart / arrive / deliver 三处均校验）
- `TransportOrderServiceImpl` 第 74 / 84 行（运单 status + schedulingStatus）
- `OrderServiceImpl` 注释明确"与 xfwl-work 的 StateTransitionValidator 保持一致"

✅ **三大跨端联动已打通（2026-10-10 全链路实测，本节原"跨端联动同步缺失"断点已解除）**：
- **提货 → 6**：`CargoController:516` `setStatus(OrderStatus.IN_TRANSIT)`（取件即运输开始）

⚠️ **遗留的架构改进（非功能缺口，勿混淆）**：上述同步逻辑**散落在 3 个 Controller/Service 方法内**，新增联动节点（如派送中 9、待派送 8 跨端可见）仍易漏改。收口建议（新建 `StateSyncService` 统一承接）**已归入《53-全量重构总体规划》R5 执行**（定案 `D-61`），不再作为独立功能需求排期。

**结论不变：不要新建状态机，也不要替换 `StateTransitionValidator`；跨端联动已工作，剩余是重构期"状态变更 → 联动对方状态"的收口。**

### 3.3 修正方案（给 Claude Code 的强制要求）

1. **复用现有一切，只做收口**（**2026-10-10 更新**：本条原为"补缺失同步桥"的强制要求，三大联动实测已打通，现转为**重构期收口建议**，归入《53》R5 执行）：**严禁新建/重写状态机**——`StateTransitionValidator` 已完备且已被调用。重构时将散落的状态联动同步逻辑（`CargoController` 提货、`TaskTransportServiceImpl` 到达、`CourierController` 妥投）**收口到一个同步组件**（`xfwl-work` 新建 `StateSyncService`，`state/sync` 包），禁止继续散落 `feign.updateById(status)`。**真实契约用 `OrderFeign.updateById`**（⚠️ 全仓无 `OrderApi` 类、`OrderFeign` 亦无 `updateStatus` 方法——2026-10-09 实测；现存唯一状态回写通路 = `PUT /order/{id}` → `OrderFeign.updateById(id, OrderDTO)`，`OrderController.java:137`，服务层经 `OrderServiceImpl.updateById()` 做流转校验、非法流转显式抛 `PdException`。重构若需专用端点 `/order/{id}/status` 须同步登记《08》）。**失败补偿**：联动写失败发 MQ 事件（复用 `OrderEventMQListener` 通道），由消费端重试 + 管理端告警；MVP 阶段允许客户端轮询 ≤15s 兜底（契约 C5），不要求强一致。
2. **双向同步**：任一端触发状态跃迁，状态机负责把**另一侧**对应状态一并算出并落库（实测已打通的链路：提货 → `Order` 6；到达 → `Order` 7；快递员妥投/拒收 → `Order` 10/11）。
3. **状态白名单**：必须经 `StateTransitionValidator` 白名单校验（允许 5→6，禁止 1→10），非法跃迁拒绝并记录。
   （❗措辞修正：是**白名单单向校验**，不是"可逆"——不支持逆向跃迁/回滚）
4. **原因码**：异常/拒收/改派必须带 `reasonCode`，便于溯源（参考调研中的 GS1/承运商原因码）。

## 4. 轨迹打通契约（核心）

### 4.1 现状断点

`xfwl-netty` 的轨迹接口（实测）：

- `GET /trace/replay?businessId=&type=` → 按 **businessId（车辆/快递员 id）** 查完整轨迹
- `GET /trace/latest?businessId=&type=` → 按 **businessId** 查最新点
- `POST /trace/page` → 支持 `transportTaskId` 过滤（但 /latest、/replay 不支持）

**断点（✅ 已解决，2026-10-10 确认）**：客户想看"我的包裹到哪了"，手里只有 `Order.id`（运单号），**没有 truckId**。`/trace/latest`、`/replay` 不接受 `orderId` 或 `transportTaskId`，导致**客户端无法查询自己订单的轨迹**。链路在查询入口断掉。
→ **已按下方契约 1 落地**：`/orderTrace/trace?orderId=`（`OrderTraceController`，2026-10-09 上线、已注册 CUSTOMER 角色，BA-01 / P0-1 ✅），按 `Order.id → 运单 → 运输任务` 解析轨迹。

### 4.2 打通契约（强制）

1. **客户查轨迹必须凭 `orderId`**：新增/改造一个客户侧轨迹查询入口，后端按 `Order.id → TransportOrder.orderId → TransportOrderTask.transportTaskId → LocationRecord.transportTaskId` 解析出轨迹，返回给客户。**严禁要求客户提供 truckId。**
2. **`/trace/latest`、`/trace/replay` 增加 `transportTaskId` 入参**（`LocationRecord` 已有该字段，无需改表），支持按运输任务查轨迹。
3. **司机/快递员查轨迹**仍按本人 `businessId` + `type` 查（不变）。
4. 轨迹数据三端同源：客户看到的轨迹 = 司机上报的轨迹 = `LocationRecord` 表，不得各端另存副本。

### 4.3 客户状态档位映射（Order.status → 客户视图）

客户小程序**只展示 7 档视图**（定案 `D-48`+`D-49`，拒收、取消各单列一档），底层仍是 `Order.status` 12 级（单一数据源，前端不私存副本，符合 C1）。

> 📌 **映射表真源 =《07-数据字典与枚举口径》§一"客户视图 7 档映射"**（2026-10-18 P2 起本文不再保留第三份副本）。档位↔状态码绑定速记：① 待取件=`1`；② 已取件待发货=`2/3/4/5`；③ 运输中=`6/7`（7 网点出库语义是"送达目的网点、进末端前置"，仍归 ③，勿望文生义归派送档）；④ 派送中=`8/9`；⑤ 已签收=`10`；⑥ 已拒收=`11`（触发退款，见 P1-11）；⑦ 已取消=`12`。

**映射实现要求**：
- 前端/BFF 用**纯查表**（按 `status` 码 `switch`）映射档位，**禁止**用区间判断或字符串匹配；
- 建议后端在 DTO 里直接返回 `customerStatus`，由服务端统一映射（《07》§一同款建议），前端不各自实现一份映射表；
- 新增 12 级状态时**只更新《07》§一映射表**（否则客户视图缺档）；
- 司机侧 `TaskTransport.status`（5 级 1~5）与快递员侧阶段映射见各自任务卡，本节仅描述客户视图；
- 状态文案可随 UI 规范本地化，但**档位与状态码绑定关系不可变**。

## 5. 实时同步方案（不引入新中间件）

遵守「**不引入新中间件**」硬约束、**复用现有能力**（按升级基线 JDK21/Spring Boot 3.5 迁移，但**不引入路线图里的新中间件**）：

## 6. 硬性契约（Claude Code 红线，违反即 bug）

> C1 **单一数据源**：任何端不得维护独立的状态副本；前端状态永远来自 `Order.status` / `TaskTransport.status`。
>
> C2 **统一状态机**：所有状态跃迁必须经由集中状态机/流转服务，禁止在业务方法里散落 `setStatus` / `feign.updateById(status)` 绕过校验。
>
> C3 **双向同步**：`Order.status` 与 `TaskTransport.status` 必须可互相推导；**实测已打通**：提货（pickUp）同步 `Order`→6、到达（任务完成）同步 `Order`→7、快递员妥投（delivered）同步 `Order`→10/拒收→11（2026-10-10 全链路实测；司机独立发车 depart 节点是否需要联动待业务拍板，现状 pickUp 即运输起点）。
>
> C4 **客户轨迹可用订单号查**：客户查轨迹只凭 `Order.id`，后端解析到 `transportTaskId`；`/trace` 接口必须支持 `transportTaskId` 入参。严禁前端要求客户传入 truckId。
>
> C5 **终态一致**：司机交付 / 快递员签收后，客户端必须在**秒级（轮询 ≤15s）**内看到对应终态与轨迹更新。
>
> C6 **不引新中间件**：实时同步只用 **RabbitMQ** / Netty / 轮询 / Spring WebSocket，不引 MQTT、Redis Pub/Sub 等栈外组件。执行口径（《06》红线 9）：① 任何**新增**消息链路（状态事件、调度指令、通知）一律走 **RabbitMQ**，复用 `xinfei.domain.event.exchange` 范式；② GPS 轨迹事件同样收口到 RabbitMQ，**不得另开第二条消息链路**。
>
> 🔴 **事件契约真源不在本文**：交换机/routingKey/队列名/生产方与消费方的**真实副作用**/幂等去重口径，唯一清单是《52-旧代码独占知识固化》§二（2.1~2.4）。删旧码后仅凭本文无法重建"揽收/签收→应收结算单"链路，须同读《52》§二。
