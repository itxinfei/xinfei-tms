## T-SEC-12 网络层 DDoS + IP 黑名单/CC 防护 ★P1

**目标**：覆盖 69 号文档 A16（网络层 DDoS，运维面）+ A9（IP 黑名单/CC 自动拉黑）；A15（慢速攻击）的 Nginx 超时参数已在 T-SEC-06（P0）落地，本卡只做回归验收。与 A1（应用层限流）形成两层防护。

**涉及文件**：
- `xfwl-gateway/src/main/java/com/xinfei/gateway/filter/IpBlacklistFilter.java`（新建，全局过滤器）
- `xfwl-gateway/src/main/java/com/xinfei/gateway/filter/`（T-SEC-01 建立的 `RateLimitFilter`/限流配置——拉黑判定挂在其 429 响应点）
- `xfwl-gateway/src/main/resources/application.yml` + Nacos `xfwl-gateway.yml`（黑/白名单配置项，热更新；A23 网关管理页是 P2，本卡不建管理页）
- `deploy/nginx/`（T-SEC-06 建立的 Nginx 配置，回归核对）
- 云 SLB/高防控制台 + 宿主 iptables（运维面操作，不进仓库；操作记录入发布/运维检查单）

**实施步骤**：
1. **Redis key 设计（A9）**（与 T-SEC-01 同 Redis 实例，同 db）：
   - 429 计数：`gateway:rl:429:{ip}`，`INCR` + 首次 `EXPIRE 60`（1 分钟滑动窗）；
   - 黑名单：`gateway:bl:ip:{ip}`，值 = 拉黑时间戳（epoch 秒），TTL = 1800；
   - 白名单/手工黑名单从配置读（步骤 3），启动加载 + Nacos 变更事件刷新，白名单**不落 Redis**（配置即真相，防误清）。
2. **IpBlacklistFilter 实现**：
   - order = -200（先于路由断言与 Same-Token 转发过滤器）：取真实 IP（T-SEC-02 A3 剥离 XFF 后写入的 exchange attribute）→ 白名单命中放行 → 黑名单命中直接响应 `429 {"code":429,"msg":"IP 已被临时封禁，请稍后重试","retryAfter":<剩余秒>}`，**不转发下游**；
   - 拉黑判定挂在 T-SEC-01 限流 429 响应点：`INCR gateway:rl:429:{ip}`，返回值 ≥100 → `SET gateway:bl:ip:{ip} <ts> EX 1800`（仅首次，重置计数避免滚动累计）。
3. **手工名单与热更新**：Nacos `xfwl-gateway.yml` 新增 `gateway.security.ip-whitelist`（办公网出口/监控探针/SLB 健康检查段，逗号分隔支持 CIDR）与 `gateway.security.ip-blacklist`（手工封禁）；网关监听配置变更重载 Bean 属性，不重启。
4. **A16 网络层（运维面）**：
   - 域名 A 记录改指 SLB/云高防 EIP；宿主真实 IP 从 DNS 可枚举面移除（`dig +short <域名>` 验证不含宿主 IP）；
   - 云侧：开 DDoS 基础防护 + 攻击事件告警接企业微信机器人（复用 C4 通道）；
   - 宿主 iptables：SYN 限速 `-A INPUT -p tcp --syn -m limit --limit 25/s --limit-burst 50 -j ACCEPT`（随后 DROP 余量）、并发连接 `-m connlimit --connlimit-above 100 --connlimit-mask 32 -j DROP`、异常包 `-m state --state INVALID -j DROP`；规则持久化（iptables-persistent/firewalld），变更前备份现行规则。
5. **A15 配置漂移核对**：逐项 grep 留档——Nginx `client_header_timeout 15s` / `client_body_timeout 15s` / `keepalive_timeout 65s` / `limit_conn_per_ip 20`；SCG `connect-timeout 3s` / `response-timeout 5s`（T-SEC-06 落地值，漂移即修）。

**验收**（可执行断言）：
- 自动拉黑：对某测试 IP 连续触发限流（`for i in $(seq 1 120); do curl -s -o /dev/null -w "%{http_code} " http://<gw>/api/auth/anno/captcha; done`，第 6 次/分起 429）→ 累计 429 达 100 后，该 IP 新请求**全路由**（含匿名接口）返回 429 且 body 含"已被临时封禁"，30 分钟后自动解封；
- 白名单豁免：白名单 IP 同强度压测全程 200/正常 429 计数，不进黑名单；
- 手工封禁：Nacos 加入测试 IP → 该 IP 下一次请求即 429（无重启）；
- `dig +short <域名>` 不含宿主真实 IP；云控制台可查 DDoS 防护记录与告警触达；
- slowhttptest/slowloris 模拟慢速连接被 15s 超时或连接数上限切断；期间 `docker stats <gateway>` 线程/连接数平稳；
- 业务回归：正常登录/下单/WS 连接不被误伤（用办公网白名单 IP 验证）。

**依赖**：T-SEC-01（限流计数器与 `ipKeyResolver`）、T-SEC-02（A3 真实 IP 写入，否则按伪造 XFF 计数）、T-SEC-06（Nginx/域名/SLB 前置）。三者均为 P0 卡，未完成不得动工。

## T-SEC-13 三端签名/防重放 + 应用层防线补强 ★P1

**目标**：覆盖 69 号文档 A7（防重放）、A8（接口签名，仅移动三端）、A14（Bot 防护 + 行为验证码升级）、A18 余项（连接数/消息频率限制）、B6（敏感数据脱敏）、B10（DataScope 数据级权限）、B8（文件上传安全——《73》ST-16 归口本卡）。

**涉及文件**：
- `xfwl-gateway/src/main/java/com/xinfei/gateway/filter/SignVerifyFilter.java`、`AntiReplayFilter.java`（新建，可合并为一个过滤器两段逻辑）；UA 初筛并入 T-SEC-02 建立的过滤器
- `xfwl-gateway/src/main/resources/application.yml` + Nacos（签名路由开关、secret 注入）
- `xfwl-auth/.../CaptchaService.java`（验证码升级；登录/验证码 controller 配合滑块校验端点）
- 三端请求层（luch-request 拦截器加签名四头）：`xfwl-mobile/customer/src/common/request/`、`xfwl-mobile/driver/src/common/request/`、`xfwl-mobile/courier/src/common/request/`
- `xfwl-netty/.../NettyServerHandler.java`（握手成功处加连接计数与消息频率限制，以实际 handler 结构落点）
- `xfwl-common/.../`（脱敏注解/工具，从 `SysLogAspect.desensitize` 抽公共）；`xfwl-auth/.../service/v1/RoleService.java` + 新建 DataScope 拦截器（`data_scope` 死字段激活）
- `xfwl-file-server/src/main/java/com/xinfei/file/controller/AttachmentController.java`（上传白名单）

**实施步骤**：
1. **A8 签名协议定版（先定协议再动码，随本卡评审确认）**：
   - 签名串：参与参数 = 全部 query 参数 + POST/PUT 的 body 原文（作为一个参数，key 固定 `body`）→ `TreeMap` 按 key 字典序 → 拼 `k=v&k=v`（忽略空值与 `sign` 本身）→ 末尾拼 `&key=<appSecret>` → HMAC-SHA256 → hex 小写（对齐《69》A8 口径与支付渠道验签同源实践）；
   - 请求头四件套：`X-Sign-Timestamp`（毫秒）、`X-Sign-Nonce`（UUID）、`X-Sign`（摘要）、`X-Sign-App`（driver/courier/customer）；
   - secret 三端独立（Nacos 加密配置/环境变量注入），登记《57》；轮换 = 双 secret 宽限（`secret.old` 保留 7 天双读）；
   - 作用域：仅三端对应网关路由前缀（xfwl-web-driver/xfwl-web-courier/xfwl-web-customer 三条路由，**以 T-SEC-03 路由清单实名前缀为准**）；管理端与 xfwl-auth 不做签名。
2. **网关 SignVerifyFilter**（order 在限流之后、路由断言之前；用 `CacheRequestBody`/`ReadBodyRoutePredicateFactory` 缓存 body 供验签）：
   - 缺任一签名头 → `403 {"code":403,"msg":"签名缺失"}`；timestamp 与服务器偏差 >300s → `400 {"code":400,"msg":"请求时间戳无效"}`；验签不过 → 403；
   - **灰度开关**：`gateway.security.sign.enabled-prefixes` 配置化，按前缀逐端开启（先 customer 灰度一周，再 driver/courier）；开关移除即回滚。
3. **三端拦截器**：三端 `common/request` luch-request 请求拦截器统一生成四头（GET 取 query、POST 取 data JSON 串）；时间戳用客户端本地时间 + 网关 ±300s 容忍，不做服务器校时（YAGNI）。
4. **A7 防重放**（与验签同链，验签通过后执行）：`gateway:replay:nonce:{app}:{nonce}` `SET NX EX 300`；已存在 → `409 {"code":409,"msg":"请勿重复提交"}`；时间窗外的 400 已由步骤 2 覆盖。支付回调等免签名端点的幂等闸门属 T-SEC-09（P0），本步不重复做。
5. **A14 Bot 防护**：
   - UA 初筛（仅 `/api/auth/anno/**`）：命中 `curl/|python-requests|httpclient|Go-http-client` → 403 + 挑战提示；**okhttp 是 uni-app App 实际 UA 之一，不得一刀切拒绝**，规则上线前先采集三端真实 UA 样本定白名单；
   - 验证码升级：`CaptchaService` 从 4 位 `SpecCaptcha` 换滑块——自研轻量方案（前端拖动组件 + 后端校验 x 偏差容差 ±5px、滑动时长 ≥300ms、轨迹非匀速）；若引入 aj-captcha 等类库属**新依赖，须先走《60》评估拍板**；
   - 登录/领券/下单敏感操作：连续失败 3 次升级二次挑战（计数 key `gateway:challenge:{user}:{ip}` TTL 10 分钟）。
6. **A18 余项（xfwl-netty）**：握手成功后按 userId 计连接数 >3 拒绝（返回错误码后关闭 channel）；单连接消息频率滑动窗 1s/20 条，超限先警告再断开；心跳空闲断开核对 `IdleStateHandler` 配置（60s）。
7. **B6 脱敏**：`xfwl-common` 新增 `@Desensitize(MOBILE/ID_CARD/BANK/NAME)` Jackson 序列化注解（规则复用 `SysLogAspect.desensitize` 抽出的公共工具）；用户/运单收发件人等 VO 列表/详情字段挂注解；Excel 导出走同一脱敏后 DTO；"查看明文"独立端点加 `@SaCheckPermission` 专用权限码并登记菜单授权。
8. **B10 DataScope**：
   - 新建 `@DataScope(dept/tenant)` 注解 + MyBatis Interceptor：按当前用户 `sys_user_role → sys_role.data_scope` 注入 `dept_id IN (...)` 谓词（落点 xfwl-common 公共包，首装 xfwl-oms/xfwl-auth 查询链）；
   - 首批装配：用户管理、订单、运单三个查询链；**多租户过滤已由 TenantLineHandler 承担，本步只补组织维度，勿重复过滤**；
   - 超管（admin）与 data_scope=全部 的角色放行。
9. **B8 上传安全**：`AttachmentController` 入口加四闸——扩展名白名单 `jpg/png/pdf/xlsx`；魔数校验（读前 4 字节比对 `FFD8FF/89504E47/25504446/504B0304`，防改后缀）；大小 ≤10MB；存储路径 `getCanonicalPath()` 前缀校验防穿越；显式拒 `svg/html/jsp`。
10. **联调与灰度**：customer 先行（网关开开关 → 三端发版 → 观察 429/403 率与业务报障 48h）→ driver/courier 跟进；全端放开后开关保留一个发布周期再清理。

**验收**（可执行断言）：
- 防重放：抓一条三端写接口请求原样重发 → 409；把 `X-Sign-Timestamp` 改为 10 分钟前重签 → 400（《73》ST-07 P1 断言）；
- 签名：去掉 `X-Sign` → 403；篡改任一 query 参数但沿用原签名 → 403；篡改 body → 403；secret 轮换期间新旧双 secret 均验签通过（《73》ST-08）；
- 管理端零影响：`/api/`管理端前缀请求无签名头照常 200；
- UA/验证码：`curl -A "python-requests/2.31" http://<gw>/api/auth/anno/captcha` → 403；三端 App/浏览器登录正常；OCR 对新滑块识别无效（自测基线 <30%）；连续 3 次失败出现二次挑战；
- WS：同账号开第 4 条连接被拒且服务端日志含拒绝原因；单连接 1s 内发 30 条消息被断开（《73》ST-28 扩展断言）；
- 脱敏：用户列表/详情/导出三处手机号均 `138****0001`；`grep -rE "1[3-9][0-9]{9}" <日志目录>` 无业务明文命中（《73》ST-24）；
- DataScope：A 部门账号查 B 部门订单/运单返回空或 403；超管不受限；
- 上传：`test.jsp` / `x.svg` / `../../etc/passwd.jpg` / 改后缀的 exe 假装 jpg 全部被拒；`test.jpg` 正常入库（《73》ST-16）；
- 回归：灰度全开后三端 H5 主链路（登录→下单/接单→完成）+ 管理端全量回归通过。

**依赖**：T-SEC-04（P0 Same-Token）必须已完成；A8/A7 三端发版与网关开关**同批联调上线**（先灰度一端，回滚 = 开关摘除前缀）；B10 依赖角色-组织数据模型稳定；滑块若引第三方库先过《60》。

## T-SEC-14 WAF 与容器基线 ★P2（二期启动时执行，勿提前）

**目标**：覆盖 69 号文档 C1（WAF）+ E5（容器基础安全）。**注意**：《69》§6 将两项列 P2——本卡为《71》附 C 预留序号的收编落点，随 P2 批次启动，不挡 P1 验收；首发前勿动（《71》附 B）。

**涉及文件**：
- `deploy/nginx/`（ModSecurity + OWASP CRS 基础规则集；或改用云 WAF 免费额度——**禁自研规则**，应用层做不全注入/XSS 规则）
- 各服务 `Dockerfile`（非 root 用户、基础镜像最小化 JRE 而非 JDK）
- `deploy/apps/docker-compose.app.yml`（`read_only: true` + tmpfs + `no-new-privileges`）
- `.gitea/workflows/`（trivy 镜像扫描 job，与《72》T-SEC-E4 的 SCA job 同期）

**实施步骤**：
1. **C1 WAF**：Nginx 挂 ModSecurity 加载 OWASP CRS，先 DetectionOnly 观察一周误报率 → 切阻断；或直接接入云 WAF（与 A16 的 SLB 同厂商优先）；白名单放行百度地图回调类大报文等已知误报源；
2. **E5 容器基线**：逐 Dockerfile 加非 root USER；基础镜像换 JRE；compose 逐服务加 `read_only: true`（tmpfs 挂 /tmp 等可写路径）与 `no-new-privileges`；CI 加 trivy 镜像扫描（CRITICAL 未处置阻断）。

**验收**：
- 注入/XSS 样本（《73》ST-14 同源样本）经 WAF 被拦且业务请求零误伤（CSP 三条回归用例联动复跑）；
- `docker exec <容器> whoami` 非 root；trivy 扫描无 CRITICAL 未处置；
- 基线变更后全业务回归通过（read_only 对临时文件/日志路径的影响逐服务核对）。

**依赖**：《72》T-SEC-E4（trivy 与依赖扫描共用 CI 体系与阻断规则）；T-SEC-06（Nginx 层承载 ModSecurity）。
