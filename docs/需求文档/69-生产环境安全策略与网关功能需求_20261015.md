## 1. 背景与目标

心飞物流 TMS（xinfei 微服务体系，网关 `xfwl-gateway` 端口 8760）准备发布到生产环境。当前系统具备基础鉴权（Sa-Token 登录态 + BCrypt + 验证码 + 登录失败 Redis 锁定 + 支付回调验签），但**不具备生产级网关防护与系统安全策略**，且存在可直接被利用的真实漏洞。

本文档给出生产发布所需的**安全策略需求**与**网关新增功能需求**，每项含优先级、来源依据、验收标准，可直接转任务卡。

**目标**：
1. 消除当前已知可被利用的漏洞（服务直连裸调、通配 CORS 等）；
2. 补齐网关"生产四件套+"：限流、请求日志+traceId、HTTPS/TLS、安全响应头、鉴权收敛；
3. 建立网络安全纵深：网络分层隔离（公网层/接入层/网关层/服务层/数据层/运维面），任一层被突破不导致全线失守；
4. 上线后 30 天内补齐防重放/签名/审计/脱敏/Bot 防护，满足等保二级核心项；
5. 以第 9 节发布闸门（测试数据/账号清理、前端卫生、企业资质、回滚预案）作为首发硬性前置；P2 未来技术栈暂缓。

## 3. 需求 A：网关新增功能（xfwl-gateway）

### A1. 接口限流 ★P0
- **需求**：引入 `RequestRateLimiter` + Redis 令牌桶。限流维度：IP（匿名接口）+ userId（登录后接口）+ 按路由覆盖配额。默认配额建议：
  - `/api/auth/anno/login`：5 次/分/IP（防爆破）
  - `/api/auth/anno/captcha`：10 次/分/IP
  - 其余登录态接口：300 次/分/user（管理端批量操作可调）
  - 全局限流：2000 次/分/IP（CC 兜底）
- **来源**：Spring Cloud Gateway 生产实践（限流是网关生产化第一道防线）
- **验收**：超限返回统一 429 JSON（含 retryAfter）；多网关实例共享同一 Redis 计数，集群下配额全局生效。

### A2. 请求日志过滤器 + traceId ★P0
- **需求**：新增全局过滤器，记录 method/path/ip/status/耗时/traceId/userId；traceId 全链路透传（网关注入 → 下游 MDC → 日志输出）；敏感字段脱敏（password、captcha、token、手机号、身份证）。
- **来源**：等保 2.0 安全审计要求；SpringBlade 三层日志注入实践
- **验收**：任一笔线上请求可凭 traceId 串起"网关日志 → 各服务日志"；日志中不出现明文口令/token/完整手机号。

### A3. 敏感头剥离 + 请求规格限制 ★P0
- **需求**：入站请求剥离所有 `X-Forwarded-*` 伪造头后，写入真实客户端 IP/协议（供 A1/A9 使用）；请求体 ≤1MB、header ≤8KB，超限拒绝。
- **来源**：网关安全基线（伪造 XFF 是绕过 IP 限流的常见手法）
- **验收**：伪造 X-Forwarded-For 不影响限流计数归属；2MB body 返回 413。

### A4. CORS 收敛 ★P0
- **需求**：`allowedOriginPattern` 从 `*` 改为白名单：管理端域名 + 三端 H5 域名（dev profile 保留通配便于联调）；白名单配置化（Nacos/环境变量）。
- **验收**：非白名单 origin 预检失败；白名单站点功能正常。

### A5. HTTPS 终止 ★P0
- **需求**：Nginx/SLB 443 → 网关 8760，全站外链强制 https，响应带 HSTS；网关容器内通信保持内网 HTTP。
- **来源**：等保 2.0 必过项（通信传输保密性/完整性）
- **验收**：http:// 访问 301 跳转 https；SSL Labs 评级 ≥B。

### A6. 端点收敛 ★P0
- **需求**：actuator 仅暴露 health（供探针，已有）；4 个 BFF 的 swagger-ui 在 prod profile 关闭（配置开关）；Druid 监控页保持关闭。
- **验收**：外网端口扫描不到 /swagger-ui.html、/actuator/env 等。

### A7. 防重放攻击 ★P1
- **需求**：timestamp（5 分钟窗口）+ nonce 一次性（Redis SETNX，TTL=窗口）。优先覆盖：移动端三端全部写接口、支付/下单/回调类接口。窗口外 400，重放 409。
- **来源**：阿里云开发者社区 timestamp+nonce 防重放方案；CSDN 工程实践
- **验收**：同一请求 5 分钟内二次提交返回 409；篡改 timestamp 重发返回 400。

### A8. 接口签名校验 ★P1
- **需求**：参数按 key 字典序排序 → 拼接 `k=v&k=v`（忽略空值）→ HMAC-SHA256(appSecret)。appSecret 按端分配（driver/courier/customer 各自独立，可轮换）。仅移动端三端强制；管理端（内网+HTTPS+登录态）不做签名。
- **来源**：开放 API 签名验签通用实践（与现有支付渠道验签同源）
- **验收**：篡改任一参数/缺签名头 → 403；secret 轮换不影响在线流量（双 secret 宽限期）。

### A9. IP 黑名单 / CC 防护 ★P1
- **需求**：基于 Redis 计数自动拉黑（如 1 分钟内触发 429 超 100 次 → 封禁 30 分钟）；支持手工加白/加黑名单配置。可与 A1 共用计数器。
- **验收**：拉黑期间该 IP 全请求拒绝；白名单 IP 不受限。

### A10. 网关集群 + Nginx 前置 ★P0（部署形态）
- **需求**：≥2 个网关实例；Nginx upstream 健康检查（`/actuator/health`）；X-Forwarded-For 透传（A1/A3/A9 依赖真实 IP）。
- **来源**：SCG 集群高可用实践（单实例网关 = SPOF）
- **验收**：kill 任一网关实例，业务无感知；滚动发布不中断请求。

### A11. 下游熔断降级 ★P1
- **需求**：Resilience4j 对下游服务按路由配置超时熔断 + fallback 响应，防线程堆积雪崩。
- **来源**：SCG 生产实践（CircuitBreaker 过滤器）
- **验收**：下游模拟挂死时网关 5s 内快速失败返回降级 JSON，网关线程池不耗尽。

### A12. 动态路由 ★P2
- **需求**：路由配置迁 Nacos（`gateway-routes.yaml`），监听变更发 `RefreshRoutesEvent` 热刷新，改路由不重启网关。
- **来源**：SCG 生产实践（静态路由改一次重启一次 = 全量请求中断）
- **验收**：Nacos 改路由秒级生效，网关无重启。

### A13. 安全响应头统一注入 ★P0
- **需求**：网关全局过滤器为所有响应注入安全响应头，按端差异化配置：
  - `Strict-Transport-Security: max-age=31536000; includeSubDomains`（HSTS，HTTPS 生效后）
  - `X-Frame-Options: DENY`（管理端/API；如有第三方 iframe 嵌入场景改 SAMEORIGIN 并登记）
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Content-Security-Policy`：管理端与 API 默认 `default-src 'self'`，**必须按业务放行**：
    - 百度地图（下单/运输页强依赖，见 57/56 号凭据表与百度 AK 事项）：`script-src`/`img-src`/`connect-src` 放行 `*.baidu.com`、`*.bcebos.com`
    - WebSocket（大屏/推送）：`connect-src` 放行 wss 域名
    - 大屏/可视化如有 CDN 资源（ECharts 等）逐项登记
  - `Permissions-Policy`：管理端 `geolocation=(), camera=(), microphone=()`；**司机端/快递员端单独放开 `geolocation=(self)`**（定位上报是核心功能，勿一刀切）
- **来源**：Nginx/Spring Security 响应头加固实践；CSP 通配策略是"配了 CSP 把地图搞挂"的高发坑，须逐端核对
- **验收**：`curl -I https://域名/api/...` 可见全部安全头；管理端下单页地图、大屏 WS、三端定位功能回归正常（CSP 回归用例：地图加载/WS 连接/定位授权各一条）。

### A14. Bot 防护与登录行为验证升级 ★P1
- **需求**：
  - 网关层 UA/工具指纹初筛：`/api/auth/anno/**` 拒绝常见工具 UA（curl/python-requests/httpclient 等）——注意排除正常客户端 UA 白名单（uni-app App、Chrome/微信内置浏览器）；
  - 登录验证码由 4 位数字图形码升级为**滑块/行为验证码**（现有 `SpecCaptcha` 可被 OCR 直接破译，是登录面真实弱点，`xfwl-auth/.../CaptchaService.java`）；
  - 登录/领券/下单类敏感操作引入行为挑战（连续失败升级挑战难度）。
- **来源**：生产系统登录防护通用做法（验证码防人机、UA 过滤防脚本）
- **验收**：脚本直连 login 返回挑战页/拒绝；真人浏览器登录体验无损；OCR 库对现网验证码识别率测试通过（接入前自测）。

### A15. 慢速攻击防护（Slowloris / Slow POST）★P1
- **需求**：Nginx 层收紧 `client_header_timeout`/`client_body_timeout`（10-15s）、`keepalive_timeout`、`limit_conn_per_ip`（单 IP 并发连接数上限，如 20）；SCG 配置 `connect-timeout`/`response-timeout`（3-5s）。
- **来源**：Web 服务抗慢速攻击基线
- **验收**：slowloris 工具模拟慢速连接被连接数限制/超时切断，网关线程与连接池不耗尽。

### A16. 网络层 DDoS 防护 ★P1（运维面）
- **需求**：公网入口（SLB/云高防或本地 iptables）配置 SYN flood/CC 防护；源站 IP 不暴露（域名解析指向 SLB 而非宿主 IP）；本地补充 iptables syn-flood 限速与异常包丢弃；与 A1/A9 应用层限流形成两层防护。
- **来源**：等保建议项（大流量 DDoS 防护）；微服务安全三维度之"网络安全"
- **验收**：SLB/防护设备有 DDoS 告警通道；`dig 域名` 不解析到宿主真实 IP。

### A17. 网络隔离与访问控制（部署面）★P0
- **需求**：
  - **Docker 网络分段**：compose 定义双网络——`frontend`（仅网关/nginx 接入）与 `backend`（中间件+全部业务服务），业务服务与中间件**只接入 backend**，不 published 任何端口（与 B1 联动）；
  - **防火墙/安全组**：公网仅放行 80/443（及 SSH 限制源 IP 至运维 VPN）；MySQL(3306)/Redis(6379)/Nacos(8848)/RabbitMQ(5672/15672)/XXL-Job(8090)/Nacos 控制台**禁止公网可达**，仅内网/VPN；
  - **控制台与运维面收敛**：XXL-Job admin（8090）、Nacos 控制台、Druid、各服务 actuator 详情一律不暴露公网，经 VPN/堡垒机访问（XXL-Job 当前弱口令 admin/123456（真源《57》§一），须与 B2 同步整改）；
  - **暴露策略**：管理端(8081)/大屏/三端 H5(8082-8084) 不直接用 IP:端口对外，统一走域名 + HTTPS（A5），按需申请证书。
- **来源**：等保必过项（网络安全域划分/边界访问控制）；微服务网络隔离实践
- **验收**：从公网 `nmap <宿主IP>` 仅见 80/443（+必要 SSH）；中间件端口公网不可达；docker network inspect 显示业务服务无 frontend 网络。

### A18. 长连接 / WebSocket 安全 ★P1（v1.6 拆分：握手鉴权最小集提前 P0）
- **需求**：xfwl-netty 长连接握手时校验 token（拒绝无凭证连接）——**此为 P0 最小集，随首发闭环**（netty 端口因设备/GPS 上报须对公网 published（见 T-SEC-05），无凭证握手=公网可直连注入/占连接，且与《10》R2-3"轨迹防伪造"阶段 0 硬闸同源——入口不设防则下游校验事倍功半）；其余维持 P1：单用户最大连接数限制（如 3）；心跳超时断开；单连接消息频率限制；SLB/Nginx 的 WebSocket 超时与空闲回收配置；`ws://` 禁止裸奔，统一 `wss://`（wss 代理 P0 已由 T-SEC-06 覆盖）。
- **来源**：长连接服务生产加固通用做法；本项目大屏/推送依赖 WS
- **验收**：无 token 握手被拒（P0）；同账号第 4 条连接被拒（P1）；wss 全量生效（P0，T-SEC-06）。

### A19. URL 规范与异常请求过滤 ★P0-P1
- **需求**：URL 长度上限（如 2KB）超限 414；禁止路径穿越（`..`、编码变体 `%2e%2e`）直接 400；非 ASCII/控制字符异常请求 400；A3 已覆盖 body/header 规格，本项补 URL 与路径穿越维度。
- **验收**：`/api/../../etc/passwd` 类样本 400；超长 URL 414；正常业务 URL 回归通过。

### A20. 路由收敛与影子 API 防控 ★P0
- **需求**：网关显式路由表之外一律 404（`discovery.locator.enabled: false` 已有，`xfwl-gateway/.../application.yml:34-36`）；上线前**核对路由清单与实际服务一一对应**（含 68 号文档已知的 `/api/v1/**` 404 预留路由的处理意见）；新增服务/接口必须经路由登记才能对外，防影子 API 与废弃接口残留。
- **验收**：扫描常见敏感路径（/actuator、/druid、/swagger、/v2/api-docs、/env）全部 404；路由清单文档化并纳入发布检查单。

### A21. TLS 配置细节 ★P0
- **需求**：仅允许 TLS 1.2+（禁 SSLv3/TLS1.0/1.1）；密码套件收敛（ECDHE + AES-GCM/CHACHA20，禁 RC4/3DES/CBC 弱套件）；证书自动续期（certbot/ACME 或云证书托管，到期前 30 天告警）；OCSP Stapling；上线前 SSL Labs 评级 ≥B（有域名条件冲 A）。
- **来源**：等保通信传输保密/完整必过项；SSL Labs 最佳实践
- **验收**：SSL Labs/SSLScan 报告 TLS1.0/1.1 与弱套件为 0；证书续期任务在监控中。

### A22. 证书与密钥管理 ★P1
- **需求**：HTTPS 证书私钥文件权限 600 且不进镜像/git；支付密钥/微信支付宝/短信 AK/SK/JWT 类密钥集中收口于 Nacos 加密配置或环境变量（与 B2 联动）；建立密钥清单（密钥名/用途/负责人/轮换周期/上次轮换时间）与轮换制度（建议 180 天）。
- **来源**：配置安全是微服务安全第一维度（密钥泄露则一切防护失效）
- **验收**：密钥清单文档化；轮换记录可查；git 历史与镜像层 grep 无私钥。

### A23. 网关管理页面（管控面）★P2（首发不做，二期轻量实现）

## 3.13 网络分层防护模型（总览）

生产网络的纵深防御分层，各需求项的落点：

| 层 | 组件 | 防护需求 | 说明 |
|---|---|---|---|
| 公网层 | SLB/云高防/iptables | A16 DDoS、A21 TLS 前置 | 源站 IP 隐藏，流量清洗 |
| 接入层 | Nginx（前置） | A5 HTTPS 终止、A13 安全响应头、A15 慢速攻击、A10 集群健康检查 | 唯一对外入口，静态资源缓存 |
| 网关层 | xfwl-gateway（SCG） | A1 限流、A2 日志+traceId、A3 头剥离、A4 CORS、A6 端点收敛、A7 防重放、A8 签名、A9 黑名单、A19 URL 过滤、A20 路由收敛、A11 熔断 | 业务流量的认证/授权/流控总闸 |
| 服务层 | 14 个 xfwl-* 后端服务 | B1 Same-Token 入站鉴权、A17 网络分段、A18 WS 安全 | 内网通信，不对外 |
| 数据层 | MySQL/Redis/Nacos/MQ | A17 隔离、B2 配置外置、C2 DB 审计 | 仅内网/VPN 可达 |
| 运维面 | XXL-Job/Nacos 控制台/堡垒机 | A17 控制台收敛、VPN 接入 | 管理流量与业务流量分离 |

**核心原则**：任一层被突破不导致全线失守——网关鉴权 ≠ 服务可裸调（V1 教训）、HTTPS ≠ 应用层免防护（限流/防重放仍必需）、内网 ≠ 可信（Same-Token + 网络分段双保险）。

## 7. 明确推荐结论

1. **P0 上线阻断集（约 25 项，详见第 6 节分期表）建议全做**，其中 **B1（服务入站鉴权）+ A17（网络隔离+端口收敛）共同关闭 V1 漏洞，最优先**；A2（日志+traceId）是后续审计与排障的地基，与 A1（限流）、A5/A21（HTTPS/TLS）、A13（安全响应头）构成网关"生产四件套+"，缺一项都不建议发布。
2. **签名+防重放只做移动端三端与支付类写接口**——管理端在 HTTPS + 登录态 + 部署收敛后性价比低，行业惯例（开放平台/App）才强制全量签名。
3. **WAF/DDoS/DB 审计不自研**，用 Nginx ModSecurity / SLB 云防护 / 数据库审计产品；应用层聚焦限流、验签、防重放、审计日志四件套。
4. **V3（dev 免锁）必须在发布前处理**：确认 prod profile 不含 dev，或发布镜像构建时校验 profile。
5. **A13 安全响应头是"配错即故障"高发区**：CSP 必须逐端核对放行清单（百度地图/大屏 WS/三端定位），上线前跑 A13 的三条 CSP 回归用例（地图加载/WS 连接/定位授权），勿一把 `default-src 'self'` 全站套用。
6. **A14 行为验证码升级建议尽早排期**：4 位数字验证码在 OCR 面前形同虚设，与 A1 登录限流互为补充，是登录面的最后一道人机防线。
7. **网关管理页面：首发不做（P2 二期）**。大厂确实都有网关管控面（ShenYu Admin / Sentinel Dashboard / Kong Manager / 云厂商 API 网关控制台），但本项目单租户部署、规则变更低频，Nacos 控制台 + 管理端只读视图可覆盖；二期随 A12 动态路由做轻量页面（A23：只读路由 + 受控黑名单 + 监控指标，路由不在线增删、写操作必须留审计），**不引入 ShenYu Admin 这类独立管控台**（换网关成本与风险远超收益）。
8. **发布闸门（第 9 节）是发布的硬性前置**，其中"测试账号/造数数据清理"是本项目当前最危险的发布项——生产库若沿用 dev 实例，《57》§2 实测的 22 个业务账号（admin/xinfei 及 20 个测试账号，口令均 123456）+ 造数业务数据等于把大门敞开，必须在发布前处理（账号清单以《57》§2 为唯一真源，勿在本文再枚举）。

- 内网 IP（65 文件）、自建 gitea 凭据（`poll-deploy.sh:25`、`.env.example:62`）、123456 散布（47 文件）——**评级降为"接受现状"**：泄露物（笔记本虚拟机访问路径）对公网攻击者无利用价值，生产换 IP 后自然失效。不做重写历史、不做转私有、不紧急改自建 gitea 口令（用户自己择机处理即可）。
- **JWT 私钥（pri/pub.key）——已闭环（2026-10-15 用户确认 pd-auth-server 彻底抛弃、永不再运行）**：密钥对不依赖网络位置，但旧栈认证服务永不运行后，公开仓库里的私钥就是"无锁的钥匙"——无法伪造任何有效 token。**无需轮换、无需重写历史、无需转私有**。附带闭环：B12（旧栈 MD5）随旧栈废弃自动关闭，保留新栈 BCrypt 纪律即可；pinda-authority 本地库 5 个密钥文件仍在 git 跟踪属可选 cleanup（仓库已私有、旧栈不跑，无实际风险）。
- **对生产发布无影响**：新栈 xfwl-* 用 Sa-Token（无 RSA 密钥对）、云服务器新 IP、生产全新数据库——历史泄露物没有一件能带进生产环境。
- 路线 B（filter-repo 重写）维持"不推荐"；路线 C（转私有）用户明确不采纳；实际执行 = 路线 A 的弱化版：A-1 已闭环，仅保留 E1 gitleaks 防复发（防止将来把真·生产凭据推进公开仓库）。
