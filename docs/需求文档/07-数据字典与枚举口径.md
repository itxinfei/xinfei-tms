# 数据字典与枚举口径（跨端唯一真源）

> **日期**：2026-10-06
> **来源**：从源码 `xfwl-service-api` 的 16 个枚举类**逐条提取真实取值**（非推测；计数口径 = `grep -rl "public enum" xfwl-service-api --include=*.java` 去 target 后实测 16）
> **用途**：三端 + 管理端 + 后端**共用同一套口径**，避免"同一个状态各端理解不同"导致的跨端 bug
> **价值**：状态值是本项目跨端 bug 的第一高发点（前端硬编码一套数字、后端返回另一套、测试按第三种理解…），本表是唯一裁决依据

---

## 〇、使用规则（先读，否则本表会被用错）

| 规则 | 说明 |
|---|---|
| **① 禁止在前端硬编码数字状态** | 一律用后端返回的 `code`，中文名只用于**展示**。前端写 `status == 6` 是 bug 源头 |
| **② 本表是唯一口径** | 文档、代码注释、数据库取值**冲突时以本表为准**（本表由源码提取） |
| **③ 新增枚举必须回写本表** | 后端加状态而本表未更新 → 视为未完成（DoD 卡点） |
| **④ 状态流转必须走校验器** | `StateTransitionValidator` 已实现且在用，**禁止绕过**（详见 §7） |
| **⑤ 中文名仅供展示** | 枚举第二个参数是**英文名**（如 `IN_TRANSIT`），中文对照取自 `OrderDTO` 注释，**两者都要以本表为准** |

---

## 〇之二、⚡ 状态码反幻觉闸（2026-10-13 · F-02 根因）

**唯一裁决**：任何状态/枚举取值以本表 §一~§六 的现行 code 为准（订单 1~12、运单 1~6、运输任务 1~5、司机作业 1~5、取派件 4 类）。历史 4~5 位数形态的旧订单状态码（23xxx 类）**已全线作废**，并于 2026-10-13 从全部需求文档就地清理，文档中不再保留旧码与换算表。

**AI 硬规则**：凡是新写状态码字面量、`if (status == ...)` 判断、SQL `WHERE status = ...` 条件、mock 数据、接口示例 JSON —— **必须回本表 §一~§六 查表**；看到 4~5 位数的订单状态值（23xxx 形态）一律视为幻觉，停手回来查此表。

## 一、订单状态 `Order.status`（12 级，核心中的核心）

> 🔴 **口径（2026-10-10 单库重构定稿，最高优先级）**：`oms_order.status` = **紧凑 TINYINT 1~12**；空库重建、不做历史数据迁移。Java 枚举 `OrderStatus` 用下表 code，**状态取值仅认下表**。
> 枚举类里只有英文名，**中文对照取自 `OrderDTO.java:144` 注释**（已交叉核对）

| 新 code（现行） | 枚举名 | 中文含义 | 客户视图档位（7 档） | 阶段 |
|---|---|---|---|---|
| 1 | `PENDING` | 待取件 | ① 待取件 | 下单后 |
| 2 | `PICKED_UP` | 已取件 | ② 已取件待发货 | 取件 |
| 3 | `OUTLETS_SINCE_SENT` | 网点自寄 | ② 已取件待发货 | 网点 |
| 4 | `OUTLETS_WAREHOUSE` | 网点入库 | ② 已取件待发货 | 网点 |
| 5 | `FOR_LOADING` | 待装车 | ② 已取件待发货 | 装车 |
| 6 | `IN_TRANSIT` | **运输中** | ③ 运输中 | 干线 |
| 7 | `OUTLETS_EX_WAREHOUSE` | 网点出库（名实见下方注释） | ③ 运输中 | 网点 |
| 8 | `TO_BE_DISPATCHED` | 待派送 | ④ 派送中 | 末端 |
| 9 | `DISPATCHING` | **派送中** | ④ 派送中 | 末端 |
| 10 | `RECEIVED` | 已签收 | ⑤ 已签收 | 终态 |
| 11 | `REJECTION` | 拒收 | ⑥ 已拒收 | 异常终态 |
| 12 | `CANCELLED` | 已取消 | ⑦ 已取消 | 异常终态 |

### ⚠️ 状态 7 `OUTLETS_EX_WAREHOUSE` 名实注释（易误解）
枚举名与字面含义是"网点出库"，但它**不是网点操作员手动做出库产生的**：在状态机联动中由**司机干线到达/交付**触发——`xfwl-web-driver CargoController#finish` 在司机 `PUT /business/cargo/finish` 时把订单置为该状态。
真实语义是"**干线货物已送达目的网点，进入末端派送前置**"（介于状态 6 运输中 与 状态 8 待派送之间）。因此客户视图仍归入 **③ 运输中** 档，不要因名字带"出库"就归到派送档。

### 客户视图 7 档映射（客户端展示用，2026-10-09 拍板）
客户不关心 12 个细分状态，只看 7 档（拒收、取消各单列一档；与《01-业务需求全景》§四映射表一致）：

| 客户档位 | 覆盖的新 code |
|---|---|
| ① 待取件 | 1 |
| ② 已取件待发货 | 2、3、4、5 |
| ③ 运输中 | 6、7 |
| ④ 派送中 | 8、9 |
| ⑤ 已签收 | 10 |
| ⑥ 已拒收 | 11 |
| ⑦ 已取消 | 12 |

> ⚠️ **映射必须查表实现，严禁区间判断**。写成 `status >= 2 && status <= 5` 是错的——一旦中间插入新状态就会漏。
> 建议后端在 DTO 里直接多返回一个 `customerStatus` 字段，由后端统一映射，前端不做区间判断。

## 七、状态机约束（枚举之外的强制规则）

### 7.1 校验器已实现，**禁止重写**

`StateTransitionValidator`（xfwl-work）已实现并在用：

| 调用方 | 行号 |
|---|---|
| `TaskTransportServiceImpl` | 243 / 287 / 331 |
| `TransportOrderServiceImpl` | 74 / 84 |

- 已覆盖：订单 12 级 + 运单双维度 + 运输任务 5 级。
- **真实缺口是"跨端同步桥"**（如司机发车未联动 `Order` 6=运输中），**不是校验器本身**。
- ❌ 严禁新建/重写状态机；✅ 缺什么补什么。

### 7.2 状态更新必须带条件（防并发覆盖）

`TaskTransport.depart/arrive/deliver` 用 `LambdaUpdateWrapper + eq(status=期望值)` 做条件更新（**状态机守卫 / CAS**），全项目**无 `@Version` 乐观锁**。

> ⚠️ 新增状态变更接口时**必须沿用条件更新**，不要直接 `setStatus()`——否则并发下会状态错乱。

### 7.3 状态流转历史表枚举口径 `work_status_transition_history`

记录各业务单据的状态流转审计（实体 `entity/state/StatusTransitionHistory`，由 `IStatusTransitionHistoryService.recordTransition(...)` 统一写入）。三个类型字段口径如下，**禁硬编码、以本表为准**：

**业务类型 `business_type`**

| code | 含义 | 关联主体 |
|---|---|---|
| 1 | 运输任务 | `work_task_transport.id`（`TaskTransportServiceImpl` 发车 / 到达 / 交付） |

> 预留：后续运单、取派件任务等如需流转审计，按域递增编码并回本表登记。
> 🚨 历史口径：旧代码此值为 `3`，新 DDL 已定为 `1`，对应常量 `BUSINESS_TYPE_TRANSPORT_TASK = 1`。

**操作类型 `operation_type`**

| code | 含义 |
|---|---|
| 1 | 状态变更 |

**操作人类型 `operator_type`**

| code | 含义 | 推导来源（网关注入的 `stationid` 头） |
|---|---|---|
| 1 | 后台人员 | 非司机 / 快递员岗的其他内部岗位 |

|---|---|

### 9.2 权限服务响应（`R<T>`）

| 字段 | 含义 |
|---|---|
| `code` | **0 = 成功**，-1/-2 = 失败 |
| `data` / `msg` | 数据 / 错误信息 |

> ⚠️ **两套响应结构并存**（业务 `Result` vs 权限 `R`），统一以 **`code === 0`** 判成功，不要只看 `isSuccess`。

### 9.3 常见错误码（联调实测）

| code | msg | 场景 | 处置 |
|---|---|---|---|
| 0 | ok | 成功 | — |
| 40003 | 缺少token参数 | 未带 `token` 头 | 前端拦截器问题 |

## 十、枚举使用规范（DoD 卡点）

开发/评审时逐条检查：

- [ ] 前端**未硬编码**任何状态数字（`status == 6` ❌）
- [ ] 状态展示**中文名**来自统一映射表，非前端自造
- [ ] 客户视图 **7 档**（§一映射表）由**查表**实现，非区间判断
- [ ] 新增状态时：改枚举 → **回写本表** → 更新状态机校验 → 通知三端
- [ ] 状态变更接口**带条件更新**（`eq(status=期望)`），非裸 `setStatus`
- [ ] 跨端对接时按**枚举类**区分 `CONFIRM`（司机作业=改派 / 运输任务=待确认）
